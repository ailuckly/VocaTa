# 提交规范

这个仓库的长期工作目标是按约定式提交写提交信息。PR 模板里要求使用这套前缀，个人开发也应保持一致。

## 格式

```text
<type>: <summary>
```

- `type` 用小写。
- `summary` 写清楚变更结果，保持简短。
- `summary` 推荐使用英文动词短语，例如 `fix login redirect`。
- 一条提交只写一件事。

如果确实需要标注模块，可以在 summary 中自然表达，或者在 PR 描述中补充说明；默认不强制使用 `scope`。

## 可用类型

- `feat`：新增功能或可见能力
- `fix`：修复缺陷
- `docs`：只改文档
- `refactor`：重构实现，但不改变行为
- `test`：新增或调整测试
- `chore`：杂项维护、脚本、依赖、构建配置
- `style`：纯格式调整，不改业务逻辑
- `perf`：性能优化
- `build`：构建系统或依赖变更
- `ci`：CI 配置变更
- `revert`：回滚提交

## 真实示例

- `docs: add deployment environment guide`
- `docs: normalize development workflow`
- `chore: normalize environment variable naming`
- `fix: keep fallback staging env copy path`
- `refactor: optimize websocket connection management`
- `refactor: remove duplicate frontend utility types`
- `feat: improve AI role creation flow`
- `test: add health check coverage`
- `chore: narrow frontend validation scope`
- `chore: update lockfile`
- `style: align web form spacing`

## 约束

- 不要用 `update`、`misc`、`wip` 这类泛化前缀。
- 不要把多个主题拼成一个标题。
- 不要让提交主题依赖上下文才能看懂。
- 如果同一批改动里既有功能又有文档，先拆成两个提交。
- 不提交无关改动。
- 不提交临时调试代码。
- 大改动拆分为多个可验证 commit。

## 推荐习惯

- 提交前先看 `git diff --stat`，确认自己只改了预期范围。
- 如果一句提交说明写不完，通常说明这次提交太大了。
- 提交前按改动范围运行 `./scripts/check.sh` 或对应模块验证脚本。

## 工具取舍

当前不引入 `commitlint`、`husky` 或 `lint-staged`。

理由：

- 个人项目优先保持简单，避免新增 hook 维护成本。
- 当前已有 PR 模板、CI、本地 `check` 脚本和文档约束。
- Git hook 可能影响临时修复、跨平台环境和 AI agent 执行流程。

后续如果协作者增多、提交格式频繁失控，或格式化噪音变多，再考虑引入这些工具。
