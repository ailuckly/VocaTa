# 发布流程硬化方案

本方案用于后续单独 PR 梳理 production release workflows。当前文件只定义审计和实施路径，
不修改 `.github/workflows/*.yml`，不删除发布入口，不改变生产部署行为。

关联 ADR：`docs/adr/0003-release-workflow-hardening.md`

## 当前状态

仓库当前有三个 production 相关入口：

| Workflow | 触发 | 作用 |
| --- | --- | --- |
| `.github/workflows/release.yml` | GitHub release published、manual dispatch | 构建版本镜像并部署 production |
| `.github/workflows/cd-production.yml` | `v*.*.*` tag push、manual dispatch | 构建组件镜像并部署 production |
| `.github/workflows/emergency-rollback.yml` | manual dispatch | test / production 紧急回滚 |

现有问题：

- 两个 production workflow 职责重叠。
- secret 命名存在差异，例如 `PROD_*` 和 `PRODUCTION_*` / 通用 `DB_*`。
- 镜像命名和 tag 策略不完全一致。
- 发布触发方式不统一：GitHub release、tag push、manual dispatch 并存。
- 回滚 workflow 与两个发布入口之间的镜像和路径假设需要核对。

## 目标

- 选出一个权威 production release path。
- 让 tag、GitHub release notes、镜像 tag、部署路径和回滚路径一致。
- 保留明确的人工 gate，避免误触发 production。
- 在删除或禁用旧入口前完成演练和文档对齐。

## 非目标

- 本轮不修改 production workflow。
- 本轮不改 GitHub secrets。
- 本轮不改 Docker image registry。
- 本轮不改变 staging 发布行为。
- 本轮不引入新的 release automation。

## Phase 1: Workflow Inventory

Outcome:

- 形成 production workflow 对照表。

检查项：

- 触发方式
- required permissions
- required secrets
- image names and tags
- deploy target paths
- generated `.env` fields
- health checks
- rollback assumptions

Acceptance checks:

- 对照表能解释 `release.yml`、`cd-production.yml` 和 `emergency-rollback.yml` 的差异。
- 不在公开文档中记录真实 secret 值、真实私钥或生产-only 明文配置。

## Phase 2: Select Authoritative Path

Outcome:

- 维护者选定一个 production release workflow。
- 另一个 workflow 标记为 legacy 或 deprecated，等待一个 release cycle 后移除。

候选判断标准：

- 触发方式是否符合 `docs/版本发布策略.md`。
- 是否能稳定构建 server / web / admin。
- 是否能产生清晰的镜像 tag 和 release notes。
- 是否能和 rollback workflow 对齐。
- 是否使用更清晰、更少的 secret 集合。

Acceptance checks:

- 选型原因写入 PR。
- 回滚方案明确。
- 如需删除 workflow，另开单独 PR 或在同 PR 中保持清晰独立 commit。

## Phase 3: Rehearsal

Outcome:

- 在 staging、dry-run 或非生产环境完成发布演练。

最低记录：

- tag
- commit
- images
- target environment
- commands / workflow run
- validation result
- rollback rehearsal result or rollback gap

Acceptance checks:

- 演练结果写入 PR 或 release notes。
- 失败项进入 `docs/开源成熟度审计.md` 或 issue。

## Phase 4: Documentation Alignment

Outcome:

- 文档只指向选定 production release path。

Touchpoints:

- `docs/版本发布策略.md`
- `docs/发布检查清单.md`
- `docs/部署环境说明.md`
- `MAINTAINERS.md`
- `README.md`

Acceptance checks:

- 文档中的触发方式、tag、回滚和验证命令与 workflow 一致。
- `CHANGELOG.md` 的 release notes 流程与 GitHub release notes 对齐。

## Phase 5: Cleanup

Outcome:

- 旧 workflow 被禁用、归档说明或删除。

Acceptance checks:

- 旧入口不会再误触发 production。
- 回滚入口仍可用于最近一个已发布版本。
- GitHub branch/tag protection 和 environment approval 规则已确认。

## 验证矩阵

| 项目 | 验证 |
| --- | --- |
| Workflow YAML | GitHub Actions syntax / actionlint 或 PR 运行 |
| Release tag | `vMAJOR.MINOR.PATCH` |
| Build | server / web / admin 镜像构建 |
| Deploy | staging 或 dry-run 演练 |
| Rollback | 回滚脚本 dry-run 或 staging 演练 |
| Docs | Markdown 链接检查、发布检查清单人工核对 |

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 误触发 production | environment approval、manual gate、单一权威入口 |
| secret 名称变更导致发布失败 | 先做 secret 对照表，不在同 PR 删除旧 secret |
| 删除仍被使用的 workflow | 至少保留一个 release cycle 的 legacy 期 |
| rollback 和 release image tag 不一致 | 在演练中记录 tag -> image -> deploy -> rollback 映射 |
| docs 与 workflow 再次漂移 | 发布 PR 必须更新 `docs/发布检查清单.md` 和 `docs/版本发布策略.md` |
