## 下一阶段候选项

### 依赖和安全自动化

- Dependabot：定期检查 Maven、npm、GitHub Actions 依赖（方案见 `docs/依赖与安全自动化方案.md`，ADR 见 `docs/adr/0002-dependency-and-security-automation.md`）。
- CodeQL：对 Java 和 JavaScript/TypeScript 做静态安全扫描（方案见 `docs/依赖与安全自动化方案.md`）。
- gitleaks 配置文件：当前 CI 已有 PR 密钥扫描；后续可把忽略规则和自定义规则落成可维护配置。
- CODEOWNERS：在维护者边界稳定后自动请求对应领域 review。

风险：会改变 GitHub 自动化行为，可能带来新 PR 噪音或误报。启用前应单独建 PR，并说明频率、忽略策略和维护成本。

### 发布工程

- Release workflow 去重和发布演练（方案见 `docs/发布流程硬化方案.md`，ADR 见 `docs/adr/0003-release-workflow-hardening.md`）。
- CHANGELOG 到 GitHub release notes 的一致性。
- Docker image 构建、版本保留和回滚说明。

风险：会影响发布节奏和分支治理。当前已有人工发布检查清单、轻量版本发布策略和 production release workflows；下一步应先做流程去重、演练和回滚硬化，不应直接叠加新的自动化入口。

### 数据库基线

- Flyway 或 Liquibase migration baseline（方案见 `docs/数据库迁移基线方案.md`，ADR 见 `docs/adr/0001-database-migration-baseline.md`）。
- 本地空库初始化脚本。
- 种子数据和测试数据策略。

风险：涉及 `vocata_*` 表结构，必须单独方案评审，不应混入文档或 Node 升级分支。

### 测试覆盖

- 管理端 Vitest 基线。
- 后端 service / controller / auth 边界测试补强。
- WebSocket streaming 的契约和回归测试（方案见 `docs/AI核心链路测试夹具方案.md`，ADR 见 `docs/adr/0004-core-ai-pipeline-test-fixtures.md`）。
- AI provider mock / fake provider 测试夹具（方案见 `docs/AI核心链路测试夹具方案.md`）。

风险：测试夹具设计会影响长期维护成本，尤其是实时链路和第三方 provider。

## 推进顺序建议

1. 先补数据库 migration baseline，解决新环境不可复现的问题。
2. 再补依赖和安全自动化，降低长期维护风险。
3. 然后梳理 release workflows，做发布演练、回滚演练和 release notes 对齐。
4. 最后系统性增强测试覆盖，优先 auth、数据写入、WebSocket streaming 和 provider wiring；其中 AI 核心链路测试夹具应先按 `docs/AI核心链路测试夹具方案.md` 落地。
