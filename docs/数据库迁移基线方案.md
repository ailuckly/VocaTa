# 数据库迁移基线方案

本方案用于后续单独 PR 引入数据库 migration baseline。当前文件只定义实施路径和验收
标准，不新增依赖、不创建 SQL migration、不改变任何 `vocata_*` 表结构。

关联 ADR：`docs/adr/0001-database-migration-baseline.md`

## 当前状态

- 后端使用 PostgreSQL、MyBatis Plus 和注解 Mapper。
- 仓库没有 Flyway、Liquibase、`db/migration/`、`schema.sql` 或 `data.sql`。
- CI 当前使用空库运行 `ContextLoadSmokeTest`，只证明 Spring context 和 Mapper 注解 SQL
  能解析，不证明业务表存在。
- `.ai-rules/database.md` 已记录真实 `@TableName` 表清单和关键数据库规则。
- README 和开发环境文档已说明新空库仍可能需要可信备份或手工 schema 准备。
- `scripts/export-schema.sh` 提供了 schema-only 导出入口，默认输出到已忽略的
  `.local/database-schema-baseline.sql`。当前它只负责把可信开发库或 staging 库导出为本地审查
  用 DDL，不等于 migration baseline。

## 目标

让一个干净 checkout 可以从空 PostgreSQL 初始化出可运行的基础业务 schema，并让后续
schema 变化进入版本化 review。

第一阶段目标不是重构表结构，而是忠实记录现有 schema。

## 范围

### 必须覆盖

- `vocata_user`
- `vocata_character`
- `vocata_character_tag`
- `vocata_tag`
- `vocata_tag_stats`
- `vocata_user_favorite`
- `vocata_conversations`
- `vocata_messages`
- `vocata_tts_voices`
- `vocata_voice_profile`
- `vocata_login_log`

### 暂不覆盖

- 生产数据导出。
- 真实 provider key、token、私钥或生产配置。
- 大规模字段重命名、表拆分、表合并。
- 物理外键。
- 业务 seed 数据的大量预置。

## 推荐路线

### Phase 1: Schema 取证

Outcome:

- 从可信开发库或 staging 库导出现有表结构。
- 对照实体类、Mapper 和 `.ai-rules/database.md` 建立字段差异清单。

Touchpoints:

- `vocata-server/src/main/java/com/vocata/**/entity/`
- `.ai-rules/database.md`
- `docs/数据库迁移基线方案.md`

Acceptance checks:

- 表清单和实体 `@TableName` 一致。
- 非统一审计字段被明确记录，例如 `vocata_character.created_at` / `updated_at`。
- PostgreSQL 数组、JSONB、UUID、timestamp 类型被明确记录。

### Phase 2: Tool 决策和 ADR 确认

Outcome:

- 维护者确认 Flyway 或 Liquibase。
- 将 `docs/adr/0001-database-migration-baseline.md` 从 `Proposed` 更新为 `Accepted`
  或新增替代 ADR。

Touchpoints:

- `vocata-server/pom.xml`
- `vocata-server/src/main/resources/application*.yml`
- `docs/adr/0001-database-migration-baseline.md`

Acceptance checks:

- 依赖新增原因、替代方案和复杂度影响已写入 PR。
- 本地、CI、staging 的启用策略明确。

### Phase 3: Baseline Migration

Outcome:

- 新增第一版 baseline migration。
- 空库可以初始化出基础 schema。
- 已有库可以采用 baseline-on-migrate 或等价策略安全接入。

Expected touchpoints if Flyway is accepted:

- `vocata-server/pom.xml`
- `vocata-server/src/main/resources/db/migration/V1__baseline_schema.sql`
- `vocata-server/src/main/resources/application*.yml`

Acceptance checks:

- 不包含真实数据或密钥。
- 主键保持 `BIGINT` + 应用层雪花 ID。
- 不引入物理外键。
- 不把 `Character`、`UserFavorite`、`CharacterTag` 强行改成 `BaseEntity` 风格。
- 对已有环境有明确 baseline 操作说明。

### Phase 4: Seed And Smoke

Outcome:

- 定义最小 seed/fake data 策略。
- CI 能在迁移后的空库上跑一个业务 API smoke。

Touchpoints:

- `vocata-server/src/test/`
- `scripts/validate-backend.sh`
- `.github/workflows/ci.yml`
- `docs/验证清单.md`

Acceptance checks:

- `ContextLoadSmokeTest` 继续覆盖启动和 Mapper 解析。
- 新增 schema-aware smoke test 覆盖至少一个读路径和一个低风险写路径。
- 测试数据不依赖真实 provider。

### Phase 5: Rollout

Outcome:

- 文档和运维流程从“手动 schema”切到“migration baseline”。
- staging 演练通过后再考虑 production。

Touchpoints:

- `README.md`
- `docs/开发环境说明.md`
- `docs/部署环境说明.md`
- `docs/发布检查清单.md`

Acceptance checks:

- 空库初始化步骤可由新贡献者执行。
- staging 发布说明包含 migration 风险和回滚路径。
- 失败时可以恢复到变更前镜像和数据库备份。

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 从实体推导 schema 导致字段类型错误 | 以可信数据库结构为准，实体只做交叉核对 |
| 已有环境重复执行 baseline | 使用 baseline-on-existing-database 策略，先在 throwaway DB 演练 |
| PostgreSQL 特有类型处理错误 | 对 JSONB、数组、UUID、timestamp 单独列检查项 |
| Seed 数据泄露敏感信息 | 只提交 fake data，不提交真实用户、provider key 或生产配置 |
| CI 变慢或不稳定 | 先新增窄 smoke，再逐步扩大覆盖 |
| 迁移失败影响 staging / production | 单独 PR、数据库备份、明确回滚步骤和发布窗口 |

## 验证矩阵

| 阶段 | 必跑验证 |
| --- | --- |
| 文档方案 | `git diff --check`、Markdown 链接检查 |
| 依赖和配置 | `./scripts/validate-backend.sh` |
| Baseline SQL | 空库 migration、`ContextLoadSmokeTest`、schema-aware smoke |
| CI 接入 | `.github/workflows/ci.yml` backend job |
| Staging 演练 | `./scripts/validate-staging-host.sh`、手工 API smoke |

## 下一步执行清单

1. 使用 `./scripts/export-schema.sh` 从可信数据库导出 schema-only DDL 到 `.local/database-schema-baseline.sql`。
2. 生成字段对照表，标记实体、Mapper 和真实 schema 的差异。
3. 维护者确认 Flyway / Liquibase 选择。
4. 更新 ADR 状态。
5. 在独立 PR 中新增依赖、baseline SQL、空库验证和文档更新。
