# 版本发布策略

VocaTa 当前还没有稳定正式版本。仓库中已经存在 production release / deploy workflows，
但正式发布仍需要人工确认版本、CHANGELOG、验证证据和回滚路径。本文件先定义轻量、
可执行的版本和发布纪律，避免 release、tag、CHANGELOG 和回滚说明各说各话。

## 分支角色

- `develop`：主要集成分支，日常功能、修复和文档变更默认合入这里。
- `master`：稳定发布线，只有准备发布或热修时从 `develop` 推进。
- `feature/*`、`fix/*`、`refactor/*`、`docs/*`、`chore/*`：个人工作分支。

PR 默认合入 `develop`。release 或 hotfix 如需合入 `master`，必须在 PR 中说明原因、
验证结果、风险和回滚方式。

## 版本号

正式 release 使用 SemVer 风格 tag：

```text
vMAJOR.MINOR.PATCH
```

- `MAJOR`：破坏性 API、部署方式、数据兼容性或核心行为变化。
- `MINOR`：向后兼容的新能力或明显用户可见改进。
- `PATCH`：缺陷修复、安全修复、文档修正或小型维护更新。

在稳定版本发布前，可以使用：

```text
v0.x.y
```

## 发布前检查

发布前必须完成：

- 确认发布范围和目标 tag。
- 更新 `CHANGELOG.md`，把 `Unreleased` 中将要发布的内容移动到具体日期。
- 按 `docs/发布检查清单.md` 完成验证、风险和回滚检查。
- 如果使用 AI agent，PR 中记录 agent 负责范围、人工复核点和未验证项。
- 如果涉及数据库 schema、部署、CI/CD、WebSocket streaming 或 provider 接线，补充 ADR。

## Tag 和 Release Notes

Tag 命名使用 `vMAJOR.MINOR.PATCH`，例如：

```bash
git tag v0.1.0
git push origin v0.1.0
```

Release notes 默认来自 `CHANGELOG.md` 对应版本段落，至少包含：

- 用户可见变化
- 安全修复
- 破坏性变化
- 验证命令摘要
- 已知问题和回滚入口

## 回滚

回滚前先确认：

- 目标环境：staging 或 production。
- 目标版本或 commit。
- 数据库是否涉及不可逆变更。
- 回滚后需要运行的健康检查。

当前 staging 回滚入口见 `docs/部署环境说明.md`。production 或自动 release 流程变更应单独
写 ADR，不和普通功能 PR 混在一起。

## 自动化边界

当前不再新增自动 changelog 生成、强制 commit hook 或额外 release automation。原因是
仓库已有 release / production deploy workflows，下一步更需要先做流程去重、发布演练、
回滚演练和文档对齐，而不是继续叠加自动化入口。

后续如果协作者增加或发布频率提高，再单独评估 release automation 的扩展范围，并通过
ADR 记录取舍。
